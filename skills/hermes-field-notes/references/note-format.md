# Note format

A note is `notes/YYYY-MM-DD-slug.md` in the store (`$HERMES_HOME/field-notes/` by default). The
metadata is a frontmatter block in a flat YAML subset: one `key: value` per line, scalars and inline
lists (`[a, b]`). No nesting. Quote any value with `:`, `#` or leading digits: `"0.21.5"`,
`"1:30"`. Keys you add yourself are kept by every command.

| Field | Required | Meaning |
|---|---|---|
| `schema_version` | yes | `1` |
| `id` | yes | the file name without `.md`; never changes |
| `title` | yes | a claim: what is wrong and what it causes — not a topic |
| `date` / `updated` | yes / no | `YYYY-MM-DD`, created / last changed |
| `type` | yes | `pitfall`, `patch` or `observation` |
| `area` | yes | `gateway`, `platform`, `cron`, `skills`, `memory`, `mcp`, `tools`, `providers`, `config`, `update`, `plugins`, `dashboard`, `other` |
| `status` | yes | see below |
| `summary` | yes | one dense line: mechanism, numbers, how to recognise it; goes into `INDEX.md` and search |
| `seen_on` | no | Hermes version where it was observed |
| `verified_identity` / `verified_at` | no | short git SHA (or identity) of the core where it was last re-checked, and when |
| `tags`, `upstream`, `candidate_skill` | no | words for search; issue/PR URL; skill name if it may become one |
| `patch_kind` | patch | `bugfix`, `customization`, `workaround` |
| `patch_short` | patch | short label for lists and alerts, ~40 characters |
| `patch_what` | no | what the patch does, in plain words for the owner; the dashboard shows it instead of `patch_short` |
| `patch_script` | no | re-apply script; printed in alerts, never run by the skill |
| `upstream_none_reason` | no | why a non-bugfix patch has no upstream link |

Statuses: `active` (true now) · `workaround` (a local fix or workaround is in place) ·
`needs-verification` (a hypothesis, not proven) · `fixed-upstream` (the core fixed it; patch retired) ·
`obsolete` (no longer relevant) · `promoted` (became a skill; the note keeps the "why").
Only `active`, `workaround` and `needs-verification` patches are checked.

## Body sections

Context · Symptom (verbatim) · Root cause (mechanism, or "hypothesis") · Fix / workaround (ready to
copy) · How to verify (observable effect) · What misled us · Caveats · Skill promotion criterion.
Patch notes add: What the patch changes · Re-apply · Why not upstream yet. Delete sections that do
not apply rather than leaving them empty: an empty heading reads as "not checked".

## Checks file of a patch (`<id>.checks.json`)

```json
{"schema_version": 1,
 "editions": [
   {"when": {"min_version": "0.21.3"},
    "targets": [{"file": "gateway/run.py", "contains": ["MY_PATCH_MARKER", "new_line_of_code()"],
                 "not_contains": ["old_line_of_code()"]}],
    "upstream": [{"file": "gateway/run.py", "contains": ["def upstream_fix("]}]},
   {"when": {"max_version": "0.21.2"},
    "targets": [{"file": "gateway/run.py", "contains": ["MY_PATCH_MARKER"]}]}]}
```

The first edition whose bounds hold is used. Paths are relative to the hermes-agent root; `..`,
absolute paths and symlinks leading outside are refused. Development builds report version
`0.0.0`; the check then uses the version in the git tag (`git describe`), and if there is none,
only an edition without bounds — otherwise the result is `UNKNOWN (version_unknown)`.

## Index

`INDEX.md` is generated by `fieldnotes.py index`: newest first, one row per note. Text above the
marker line is yours and survives regeneration; never edit the table by hand.
